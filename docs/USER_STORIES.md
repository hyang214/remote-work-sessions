# User Stories

[中文](USER_STORIES.zh-CN.md) | English

This document lists product user scenarios only. Quality gates, release checks, and evidence-format rules live in [`QUALITY_GATES.md`](QUALITY_GATES.md).

A user story can be marked verified only when the acceptance criteria have matching evidence. If a scenario is listed as open, it is intentionally not part of the completed release-supported scope yet.

## Story Matrix

| ID | Status | User Story | Acceptance Criteria | Current Evidence Or Gap |
| --- | --- | --- | --- | --- |
| US-001 | Verified | As a new user, I can install the tool and get one command named `rws`. | The package is `remote-work-sessions`; the installed binary is `rws`; `rws --help` and `rws --version` work; no `rsw` command is introduced. | Smoke installs the package into a temporary global prefix, checks the binary, version, help surface, and absence of `rsw`. |
| US-002 | Verified | As a new user, I can run one setup flow instead of stitching together multiple manual steps. | `rws setup` covers local config, local SSH checks, first remote connection before any session cwd selection, optional key setup, numbered progress while dependency/prompt/verification work is running, remote dependency setup, final connect/shpool device verification, and optional initial session creation after the device is ready. | Smoke covers config-only setup and non-interactive setup without a cwd. Podman E2E covers clean client/server setup with real SSH, optional setup session cwd picker, numbered setup progress messages, and real upstream `shpool`. |
| US-003 | Verified | As an uninitialized user, I get a clear next step instead of confusing command failures. | Daily commands fail loudly before setup and tell the user to run `rws setup`. | Smoke and E2E execute uninitialized daily commands and assert the setup guidance. |
| US-004 | Verified | As a user with only remote username/password access, I can complete first-time setup interactively. | Setup prompts through SSH for password or host-key confirmation before any session directory selection; wrong passwords produce a clear error without asking unrelated later questions; passwords are never read, stored, or logged by `rws`. | E2E covers wrong password before the optional session cwd picker, host-key confirmation, password-login setup, and scanning generated config for password absence. |
| US-005 | Verified | As a user, I can choose how SSH keys are handled during setup. | Setup supports creating a dedicated key, reusing an existing key, or skipping key setup; generated public keys can be installed through the established interactive SSH connection or a bootstrap key; non-interactive key installation without a bootstrap identity fails loudly. | Smoke covers key reuse, `--force-key`, and non-interactive install-key failure. | US-006 | Verified | As a user on a clean local or remote machine, missing prerequisites are handled by setup when possible. | Setup checks local OpenSSH tooling; missing remote `shpool` is installed with the pinned version; Cargo/build dependencies are installed through the release-supported package manager path when needed; session directories are created when sessions are created. | E2E covers clean Alpine local OpenSSH install, real remote `apk` dependency install, real `cargo install shpool --version 0.9.8 --locked`, and real session cwd creation. | US-007 | Verified | As a user, I have a simple config model that lives inside the tool's config directory. | User config lives under `~/.config/rws/`; device files live under `devices/`; default selection uses `device=`; sessions use `default_session=`; unknown legacy keys fail loudly. | Smoke covers default config, custom `--config-dir`, device files, default selection, and rejection of legacy `profile` and `name` config keys. |
| US-008 | Verified | As a user, I can set up a device once and create multiple sessions without re-entering the host. | `rws new <session> --cwd DIR` or `--pick-cwd` creates or attaches another session on the selected device; `rws --device <device> new <session>` uses that device; no host is required after device setup. | E2E runs `rws --device e2e new review` and `rws --device e2e new picked --pick-cwd`, then confirms sessions through JSON listing. |
| US-009 | Verified | As a daily user, I can run the common remote-session commands with short, predictable syntax. | `rws`, `rws f`, `rws s`, `rws c`, `rws sh`, `rws sessions`, `rws ls`, `rws bg`, `rws run -- ...`, `rws d`, `rws k`, `rws doctor`, `rws devices`, `rws remove`, and the explicit `key`/`device`/`session` entity commands are documented and tested where applicable; common options have standard short and long forms. | Smoke checks help and README command-table coverage, `rws help scenarios`, `rws help commands`, and short-option parser paths. E2E runs the daily command set and session entity commands against real SSH/shpool where applicable. |
| US-010 | Verified | As a user with long-running remote work, sessions survive disconnects and can be reattached or cleaned up. | Background session creation works; force attach updates real shpool connection state; detach is safe to rerun when already disconnected; kill removes sessions. | E2E verifies `bg`, force reattach timestamp change, disconnected status after PTY close, idempotent detach, and kill cleanup. |
| US-011 | Verified | As a user with more than one remote machine, I can list, choose, and remove devices. | Devices are listed from `devices/`; `--device` chooses a device; removing the default device chooses another default when available; when no devices remain, later commands ask for setup. | Smoke and E2E verify device listing, device override, remove aliases, default rewrite, and last-device removal returning to setup guidance. |
| US-012 | Verified | As an existing user, I can rerun setup safely. | Repeated setup lets interactive users continue with saved values, reset and replace the device, or quit; repeated non-interactive setup rewrites the selected device in the current format; existing keys are reused unless forced; public keys are not duplicated; existing pinned `shpool` is reused instead of reinstalled. | Smoke verifies local key reuse and `--force-key`. E2E verifies existing-device continue/reset choices, repeated setup, authorized-key de-duplication, existing-key setup, and reuse of existing pinned shpool. |
| US-013 | Verified | As a security-conscious user, I can reason about what secrets the tool handles. | `rws` does not store passwords, private key contents, tokens, or secret environment variables; interactive password and sudo prompts are owned by SSH/sudo; setup states the remote files it may modify before writing remote state. | Smoke checks security claims and scans for obvious secret-storage patterns. | US-016 | Verified | As a human or AI agent following the docs from a clean environment, I can complete setup reliably. | Setup docs describe the new-user path, password path, non-interactive path, dependency path, idempotency, device/session separation, optional initial session creation, and command usage without relying on chat context. | E2E completes from a clean environment. | US-020 | Verified | As a user, invalid device, session, and config values cannot corrupt files or execute unintended paths. | Device names and session names reject empty values, `/`, `..`, path traversal, and values that break config layout or remote command construction; config files reject unknown keys; one-off overrides do not persist unexpected values. | Smoke verifies invalid setup/init/remove/new/bg/d/k values, unknown config keys, and one-off overrides not rewriting config. |
| US-021 | Verified | As a user in a pre-managed environment, I can use setup and overrides without unintended installs or config rewrites. | `--remote-install check` verifies and fails clearly without installing; `--remote-install skip` skips remote dependency setup; `--no-verify` avoids network verification for config-only generation; `--no-create-session` avoids session creation; one-off `--host`, `--cwd`, and `--session` overrides do not rewrite device files. | Smoke verifies config-only paths and one-off overrides. ## Current Supported Coverage

The current verified scope is macOS smoke coverage plus Alpine Linux container E2E with real SSH and real upstream `shpool`.

The release-supported automatic install path is Alpine/apk for local OpenSSH and remote Cargo/build dependencies, plus pinned upstream `shpool` through Cargo. Other package-manager branches in code (`apt-get`, `dnf`, `yum`, `pacman`, `zypper`, and `brew`) are best-effort until a real E2E job covers that platform.

## Open User-Scenario Gaps

The following product scenarios are not completed yet and must not be reported as passed:

- non-default SSH routing such as non-standard ports or jump hosts (`US-033`);
- interrupted setup during a long-running remote dependency installation; `US-025` covers failed setup cleanup, optional setup session creation, and interrupted attach only.
